# 桌次管理：素食者的人選、桌次與份數

**日期：** 2026-08-10
**狀態：** 設計待核可
**橫跨 repo：** `jdc-line-gas`（後端／資料）＋ `jdc-line-liff`（前端／Excel）

---

## 1. 問題

桌次管理頁（`stats.html` → 桌次管理）現在查不到誰吃素。葷素資料存在，但到不了這一頁：

- 同仁的葷素填在**活動回覆表「葷素」欄**（`index.html` 送出、`answers.js` 驗必填、`stats.js:46` 只拿它算總數）
- `getSeatingBoard`（`Code.js:3819`，桌次管理的**唯一**資料源）組 `seats` 物件時只帶 `姓名／單位／職稱／員編／桌次／異動`，**沒帶葷素**
- 來賓（廠商）**根本沒有葷素欄位**，`GUEST_HEADER` 只有 `註記` 這個自由文字欄

所以前端無論怎麼改版面都做不到——後端要先補資料。

## 2. 三個使用場景（使用者確認）

| 場景 | 誰用 | 要什麼 |
|---|---|---|
| 當天給餐廳／宴會廳出菜 | 使用者 → 餐廳 | **哪一桌幾份**（附姓名供核對）。**不需要精確到座位**（拍板：「知道哪桌幾份就好」） |
| 排位時邊看邊排 | 使用者 | 一眼看出哪桌有幾個素食者，決定集中或分散 |
| 當天現場臨時查某個人 | 使用者（手機） | 「我點的素食呢」→ 馬上查到這個人在幾桌 |

## 3. 不做什麼

- **不在正式座位表的座位格標素食**（使用者拍板）。理由：那要求每個人真的坐在自己位子上才準，而圓桌宴會做不到；標了反而給服務生錯誤的確定感。
- **不改來賓檔為一人一列**（使用者拍板）。現有各單位回報的舊格式檔還在用，改格式等於全部重做。
- **不做素食者的自動排位**（集中／分散由使用者手排決定，系統只呈現）。

## 4. 資料層（`jdc-line-gas`）

### 4.1 `getSeatingBoard` 每個 seat 多帶 `veg`

```
seats.push({ kind:'emp', ..., veg: <bool> })
seats.push({ kind:'guest', ..., veg: <bool> })
```

- **同仁**：沿用 `stats.js:46` 的既有判定 —— 回覆表「葷素」欄正規化後 `=== '素食'`。**判定只能有一套**，兩處若各寫一次，日後改判定會漏改一邊。
- **來賓**：見 4.2。

### 4.2 來賓的葷素

⚠️ **兩張表的形狀不同，欄名不可共用**：

| | 形狀 | 新欄名 | 值 |
|---|---|---|---|
| 來賓表（Google Sheet，系統存的） | **一席一列**（展開後） | `葷素` | `素食` 或空白 |
| 來賓上傳檔（使用者手上的 Excel） | **一列一廠商**＋`參加人數` | `素食人數` | 整數 |

- `GUEST_HEADER`（`Code.js:3631`）加入 `'葷素'`。
- **舊表不會壞**：`getGuestSheet_`（`Code.js:3634`）已有自癒 —— 缺的欄自動補到最右，且全檔一律照**欄名**存取、不依賴欄位順序。無需手動改試算表。
- `addGuests` 的 `pick()` 加一個 case：`'葷素' → g.veg ? '素食' : ''`。
- 展開規則（前端 `upGuests` 讀上傳檔時）：一家廠商 `參加人數 = 5`、`素食人數 = 2` → 展開成 5 個席位，**席位序號 1、2 帶 `veg=true`**，3～5 為 false。

### 4.3 就緒旗標 `vegReady`

`getSeatingBoard` 回傳頂層多一個 `vegReady: true`。

**為何需要**：前端上版而後端沒上時，`s.veg` 全是 `undefined` → 畫面會顯示「素食 0 份」。**那是一個看起來完全正常、但會讓人少訂餐點的數字**——比報錯更危險（同型教訓見 memory `feedback_fire_and_forget_hides_outage`）。前端讀不到這個旗標就明寫「素食資料尚未就緒」，不顯示任何份數。

## 5. 前端（`jdc-line-liff`）

### 5.1 既有兩個視圖加標記

- **磚（依桌次／依單位）**：人數後面接 `素 N`。**沒有素食者的磚不顯示這段**，避免整片 `素 0` 的視覺噪音。
- **明細列**：素食者名字後掛一個「素」小標，沿用現有 `.chg`／`.gtag` 那套小標語彙，不新增顏色系統。

### 5.2 第三顆 pill「🥬 素食」——以人為單位、可操作

切到這個視圖時，`seat-board` 直接列出**全部素食者**（不經磚、不必再點一層）：

- 每列：姓名／職稱／單位／`N 桌`（未排桌者顯示「未排桌」標記）
- 每列沿用現有的「移桌」「🔳」「⬇QR」動作 —— 現場查到人可以直接處理
- 這個視圖隱藏 `scope-row`（已排桌／未排桌切換）：未排桌的素食者**必須**跟已排桌的一起出現，否則現場會漏人

### 5.3 常駐彙總卡「🥬 素食彙總」——以桌為單位、唯讀

放在座位表卡下方，不必切換就看得到（現場最急的兩個用途都不該多一個動作）：

```
3 桌    2 份    王小明、李小華
5 桌    1 份    陳大同
未排桌  1 份    （來賓）某某工程行
────────────────────
合計    4 份
```

- 「未排桌」單獨一行，代表**還沒定位的份數**（給使用者看的缺口，不是給餐廳的）
- `vegReady` 為假時，整張卡改顯示「素食資料尚未就緒（後端未更新）」，**不顯示任何數字**

### 5.4 兩份 Excel

- **排位用檔**（`buildSeatingAoa`）：下方分類名單的素食者名字後加「（素）」。來賓欄同樣適用——同一家廠商 5 人 2 素，該欄會出現 5 個同名列、其中 2 個帶「（素）」。
  上傳排位結果時 `parseSeatingUpload` 的 `clean()` 已經會去掉 `（…）` 註記（`seating.js:235`），所以**整個名字複製到座位格再上傳不會誤判成別人**。此行為現在就存在，不是新加的。
- **正式座位表**（`buildFormalAoa`）：座位格不標；表格**最下方**附一段「桌號／素食份數／姓名」。
  理由：那份本來就是要印出來給人看的，彙總長在同一張紙上，比另開一份檔案可靠（另開的那份一定會有人忘記帶）。

## 6. 已知誤差（要寫進畫面，不能只寫在文件）

1. **同一家廠商被拆到兩桌時**，素食份數會算在席位序號較前的那桌，可能與實際不符。彙總卡對這類桌次標註提示，由使用者手動調整。
2. **彙總的分母是「已確認參加的人」**（`getSeatingBoard` 只收 `出席 = 參加` 的回覆），不是全公司。沒回覆的人不在名單裡，也不會被算成葷食。
3. **來賓的素食人數靠各單位回報**，系統無從驗證；舊格式檔案沒有這欄，一律當 0。

## 7. 測試

純邏輯集中在 `assets/seating.js`（已有 `node --test`）：

| 函式 | 案例 |
|---|---|
| `vegSummary(seats)` | ①一般桌 ②該桌零素食（不得出現在彙總） ③未排桌的素食者單獨成行 ④同一家廠商跨兩桌 ⑤全部無素食（回空、合計 0） |
| `expandGuestRow(row)`（來賓展開，**從 `stats.html` 內聯抽出**） | ①5 人 2 素 → 席位 1、2 為素 ②素食人數 > 參加人數（取小值，不得產生比席位多的素食） ③沒有素食人數欄（舊檔）→ 全 false ④參加人數 0 → `seatNo=0` 不佔位 |

`expandGuestRow` 現在埋在 `stats.html` 的 `upGuests()` 裡、沒有任何測試；補這個欄位正好把它拉出來成為可測的純函式。**這是本次唯一的順手重構，不擴大範圍。**

前端呈現（磚、標籤、彙總卡、第三顆 pill）依 memory `feedback_ui_change_needs_real_page`：**必須實際開頁面看過**，不能只靠單元測試與靜態審查。
